Reference
What each component does
8 are language models. 1 is a Python subprocess. That split is the whole story.
LLM
planner
temperature 0.4 · always first node

Reads the user query and writes the entire plan as JSON. Decides which skills are needed, in what order, what depends on what. Doesn't do work itself — just designs the graph. Like a project manager breaking a request into tasks.

LLM
researcher
temperature 0.7 · multi-turn tool loop

The internet fetcher. Issues web searches (DuckDuckGo, Brave, Wikipedia API) and fetches pages using Crawl4AI. Decides which URL to fetch, whether the content answers the question, or whether more search is needed. Returns raw text.

LLM
retriever
temperature 0.2 · queries FAISS

Same idea as researcher but searches the agent's own indexed knowledge base instead of the open web. Goes through FAISS vector similarity. Used when the agent has previously indexed documents relevant to the query.

LLM
distiller
temperature 0.1 · auto-triggers critic

The extractor. Given a blob of text from a researcher, pulls out specific structured fields. "From this Wikipedia page, give me birth year, nationality, field, discovery." Returns clean JSON. Marked critic: true in YAML — automatically gets a critic node after it.

LLM
summariser
temperature 0.3 · condenses

Takes long content and produces a shorter version preserving the key information. Used when downstream nodes need an overview rather than the full text.

LLM
critic
temperature 0.0 · auto-inserted

The judge. Reads another node's output and returns pass or fail with a one-line rationale. Temperature 0.0 — same input must give same verdict every time. On fail, next node is skipped and a recovery planner is queued.

LLM
coder
temperature 0.2 · auto-triggers sandbox

The Python writer. Outputs JSON with two fields: code (the Python) and summary (natural-language description with the computed answer). Coder skill has internal_successors: [sandbox_executor] — sandbox is auto-attached.

SUBPROCESS
sandbox_executor
NOT an LLM · 0.0s in logs · pure Python

Takes the Python code from the coder and runs it in an isolated subprocess. Env vars scrubbed (only PATH, HOME, LANG, LC_ALL, LC_CTYPE). 30s timeout. 1 MB output cap. Result logged to NodeState but not shown to user — the formatter is. This is the "verify" in trust-and-verify.

LLM
formatter
temperature 0.3 · always last node

The presenter. Always the last node in every graph. Reads everything above it — researcher outputs, distiller fields, critic verdict, coder summary — and writes the final human-readable answer. The answer the user sees comes from here. Never runs code, never fetches URLs. Just composes text.

Deep dive
Critic + Coder + Sandbox
The three components that together implement trust-and-verify.
🧑‍⚖️ Critic — the judge

What it is: An LLM that looks at another node's output and says "good" or "bad". Returns exactly {"verdict": "pass"|"fail", "rationale": "one sentence"}.

When it runs: Auto-inserted on every outgoing edge from a distiller. You never ask for it — the orchestrator puts it there because the YAML says critic: true.

Why temp 0.0: Pass/fail must be deterministic. Same input on Tuesday and Wednesday → same verdict. Randomness would make recovery fire stochastically — impossible to debug.

Example (Marie Curie): Distiller extracted all 4 fields cleanly. Critic returned pass in 0.9s. Formatter ran. User saw the answer.

Honest limit: Critic is reliable for things the model can read (factual presence, structural completeness). It's a rubber stamp for things it can't compute (syllable counts, exact arithmetic). The forcing-query example: approved a 5-7-5 haiku claiming it was 4-6-4 — three times. The wiring is correct. The verdict quality is a prompt problem.

💻 Coder — writes Python

What it returns: A JSON object with two fields:

{
  "code": "pop = {'Japan': 123000000}\n# compute...\nprint(result)",
  "summary": "Japan has the highest GDP/capita at ~$34,146"
}

Why two fields: Two downstream nodes need different things. Formatter reads summary to write the user's answer. Sandbox reads code to actually run it.

Auto-successor: YAML says internal_successors: [sandbox_executor]. Whenever a coder node completes, the orchestrator silently appends a sandbox after it. The planner doesn't have to ask.

🛡️ Sandbox — NOT an LLM

What it does: Reads the coder's code field. Writes it to a temp file. Runs subprocess.run(["python", "script.py"]) with a restricted environment. Returns stdout, stderr, exit code.

The restrictions: Env vars scrubbed to 5 (PATH, HOME, LANG, LC_ALL, LC_CTYPE). Fresh temp dir deleted on exit. 30s timeout. 1 MB stdout cap.

Usability boundary, not security: Catches mistakes (infinite loops, env leaks). Does NOT catch attacks — no network isolation, no filesystem restriction outside tmp. Fine for student code.

The giveaway in logs: sandbox_executor complete (0.0s) — zero seconds because there's no network round-trip to an LLM. Just a subprocess call.

Where the result goes: Logged to NodeState on disk. NOT shown to user. The formatter reads the coder's summary, not the sandbox's stdout. This is what makes it trust-and-verify in one graph.

The line to land
The critic judges. The coder writes Python. The sandbox runs it. Two of those are language models. One is not — and that's where the agent stops reasoning about computation and actually does it.
Query 1 · Minimum DAG
"Say hello"
Session: s8-f4271e9a Nodes: 2 Wall-clock: 10.58s
What happens

The agent receives "Say hello". The planner looks at this and says: this needs no research, no math, no extraction — just produce a greeting. So it skips all the heavy machinery and sends the query directly to the formatter, which writes "Hello! How can I help you today?"

What this proves
The smallest possible DAG the architecture can produce. The planner is smart enough not to over-engineer simple requests.
Query 2 · Sequential chain + auto-critic
Claude Shannon Wikipedia
Session: s8-76dba0d3 Nodes: 5 Wall-clock: 21.66s critic auto-inserted
What happens

A sequential chain. The planner sees the query needs three steps: fetch the page, pull out the facts, then present them. So it builds: researcher → distiller → critic → formatter.

The researcher fetches the Wikipedia page using Crawl4AI. The distiller reads that text and extracts the structured fields. Because the distiller is marked with critic: true in the YAML, the orchestrator automatically inserts a critic node — you didn't ask for it. The critic returns pass. The formatter writes the final answer: born 1916, died 2001, three contributions to information theory.

What this proves
Auto-insertion of the critic. The distiller pipeline. Sequential dependencies where each node truly needs the previous one's output.
Query 3 · Parallel fan-out
London, Paris, Berlin populations
Session: s8-b3a799cb Nodes: 5 Wall-clock: 58.18s saved 69s vs sequential
What happens

The parallel fan-out demo. The planner sees three independent sub-tasks (one per city) and emits three researcher nodes at the same level. All three start at the same moment under asyncio.gather.

In the logs you can see tool calls interleaved — Paris fetching from Statista, Berlin from Wikipedia, London from worldpopulationreview — all in the same time window. The researchers finished at 40.7s, 48.5s, and 28.4s. The formatter waited for the slowest (Berlin at 48.5s) before starting.

The key math: if these had run sequentially, total = 40.7 + 48.5 + 28.4 = 117.6 seconds. They ran in parallel, so the parallel layer cost was just 48.5s — the slowest branch. Saved 69 seconds.

Final answer: Berlin (3.91M) and Paris (2.04M) are closest, differing by 1.87M.

What this proves
asyncio.gather parallelism. The cost of a parallel layer is max(branches), not sum.
Query 4 · Graceful failure
/nonexistent/path.txt
Session: s8-aa865446 Nodes: 2 Wall-clock: 9.02s no tool dispatched
What happens

The planner reads "read this file that doesn't exist" and recognizes immediately: there's no skill in the catalogue that reads local files, and even if there were, the file doesn't exist. So it doesn't dispatch any tool. It emits just a formatter with a failure note in the inputs.

The formatter writes: "I am unable to read the file at /nonexistent/path.txt because it does not exist."

What this proves
The planner can fail-fast by planning. It doesn't blindly attempt impossible tasks. No tools wasted. No retry loops triggered.
Query 5 · Resume from disk
Lagos, Cairo, Kinshasa
Session: s8-c0731757 Nodes: 5 Wall-clock on resume: 42.07s killed mid-gather + resumed
What happens

The persistence demo. The query was started, three researchers launched in parallel, and Ctrl+C was hit while they were still working — the traceback shows it killed mid-asyncio.gather. The graph was saved atomically to disk as it went.

Then: python run.py "" --resume s8-c0731757. The Executor read graph.json from disk, found the running nodes, reset them to pending, and continued. The researchers re-ran, the formatter combined the results.

Final answer: Kinshasa is growing fastest at 4.36% per year, followed by Lagos at 3.78% and Cairo at 1.07%.

What this proves
Atomic JSON writes. Resume contract. The session is the durable artifact — you can kill the process at any moment and pick up where you left off.
Query 6 · Biggest DAG · coder + diamond
Japan, Brazil, Nigeria GDP per capita
Session: s8-0113fe36 Nodes: 8 Wall-clock: 53.80s coder + 2 sandbox
What happens

The most complex run. Planner produces a graph with three researchers in parallel, feeding into a coder, which fans out to a formatter AND two sandbox_executor nodes.

The coder writes actual Python that computes GDP per capita. Because the coder skill has internal_successors: [sandbox_executor] in the YAML, the orchestrator automatically inserts sandbox nodes after it — that's why there are two: one queued by the planner explicitly and one auto-inserted. The sandbox runs the Python in an isolated subprocess to verify the math. The formatter reads the coder's summary and presents the answer.

Final: Japan has the highest at ~$34,146 per capita, Brazil $10,616, Nigeria data unavailable.

What this proves
The diamond shape — trust and verify. The coder writes code; the sandbox runs it; the formatter writes the human answer. Real execution alongside LLM reasoning. The Python output grounds the arithmetic claim in actual computation, not LLM guessing.

Query 8 · Critic exercise (FAIL path probe)
"A minor historical figure"
Session: s8-427a6cde Nodes: 5 Wall-clock: 25.18s interesting interpretation
What happens

Same pipeline. The planner interpreted "a minor historical figure" loosely and routed to Claude Shannon (interesting choice — Shannon is not minor at all). The critic fired again (1.1s). All four fields present.

What's interesting: this query was designed to test the FAIL path of the critic. In this particular run, the chosen figure had all fields available, so the critic returned pass anyway. The mechanism is wired correctly — what triggers a fail verdict is a policy decision living in the critic's prompt, not a wiring problem.

What this proves
The critic mechanism is consistent. Whether it returns pass or fail depends on the prompt + the actual data, not the wiring. Mechanism vs policy — Rohan's core distinction.
Query 9 · Coder + sandbox · honest answer
Tokyo, Delhi, Shanghai within 5%
Session: s8-d82bb3e6 Nodes: 7 Wall-clock: 51.68s computed 6.05%
What happens

The coder demo. Three researchers run in parallel fetching populations (Delhi 32.4s, Tokyo 20.6s, Shanghai 36.7s). The coder receives all three numbers and writes Python to compute pairwise percentage differences. The sandbox runs the code. The formatter presents the result.

Critical observation: the formatter's answer is honest — "Delhi (23.39M) and Shanghai (24.85M) differ by 6.05%, so none meet the under-5% threshold." A formatter alone might have hedged with "approximately similar." The coder + sandbox gave the precise 6.05% number, and the formatter correctly concluded none qualify.

What this proves
Computation beats text-guessing. The architecture grounds precise numeric claims in real arithmetic.
Query 10 · Custom skill demo
Convert 330 metres to feet
Session: s8-3d347e0d Nodes: 3 Wall-clock: 8.84s no Python touched
What happens

The custom skill demo. A new unit_converter skill was added to agent_config.yaml with a prompts/unit_converter.md file. Zero changes to flow.py, the Executor, or any other Python file.

The planner sees the query, recognizes it matches the unit_converter skill, and routes to it. The skill produces the conversion: 1,082.68 feet. The formatter presents it.

What this proves
Adding a skill = YAML edit + one prompt file. Nothing else. This validates Rohan's architectural rule: touching the Executor for a new skill is a bug.
