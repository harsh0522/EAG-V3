Core Concept

What is MCP?

Model Context Protocol is a standard for connecting AI models to external tools — like a USB standard for AI capabilities.

Why MCP instead of custom glue code?

✅ With MCP

  • Tools are self-describing — model asks "what can you do?" and gets a schema back
  • Swap Gemini → Claude → GPT-4 without changing any tool code
  • Tools run in a separate process — isolated, restartable
  • Standard transport (SSE/WebSocket) — works over network too

❌ Without MCP

  • Every AI SDK has a different function-calling format
  • Tool schemas must be manually maintained in sync with the model's API format
  • Tight coupling — tools and model live in the same codebase
  • No standard — every team invents their own

Transport: Server-Sent Events (SSE)

The MCP server in this project uses SSE transport. The agent opens a persistent HTTP connection to http://127.0.0.1:8000/sse. Tool calls are sent as HTTP POST, results stream back as SSE events. FastMCP handles all of this automatically.

mcp_server.py

MCP Server — Every Function Explained

Helper / Utility Functions

ensure_data_files()

Runs once at startup. Creates data/ directory and empty companies.json + agent_log.json if they don't exist. Ensures the server never crashes due to missing files.

load_companies() → dict

Reads companies.json and returns it as a Python dict. If the file is missing or corrupt, returns an empty dict instead of crashing.

save_companies(data)

Atomic write. Writes to a .tmp file first, then renames it to the real file. This prevents data corruption if the process is killed mid-write.

def save_companies(data):
    tmp = COMPANIES_FILE.with_suffix(".tmp")
    tmp.write_text(json.dumps(data))
    tmp.replace(COMPANIES_FILE)  # atomic!
load_logs() → list

Reads agent_log.json and returns it as a list of operation dicts. Same safe fallback pattern as load_companies.

append_log(operation, company, tool)

Appends a single log entry with timestamp, operation, company, and tool to the log file. Called by every tool on every action so the Agent Log tab always has complete history.

fetch_company_info(company_name)
Tool 1 — Web Scraper
@mcp.tool()

What it does: Takes a company name, fetches structured information from two public APIs, and returns a dict with 9 fields.

Step-by-step inside the function

  1. Build empty result dict — pre-fills all 9 keys with None so the structure is always consistent even if some sources fail.
  2. Wikipedia REST API — calls https://en.wikipedia.org/api/rest_v1/page/summary/{company}. Extracts: description, first 600 chars of summary, and the source_url.
  3. DuckDuckGo Instant Answer API — calls the DDG JSON API. If Wikipedia didn't return a description, DDG fills it in. Also parses the Infobox section for: founded, headquarters, industry, key_people.
  4. Regex fallback for founded year — if founded is still empty, runs a regex on the summary text to find a 4-digit year after the word "founded".
  5. Log the operation — calls append_log("fetch", company_name, "fetch_company_info").
  6. Fill N/A for blanks — any field still None or "" gets set to "N/A" so downstream code never sees None.

company_file_crud(operation, company_name, data)
Tool 2 — Database Manager
@mcp.tool()

What it does: A full CRUD interface over data/companies.json. The AI model calls this to save, read, update, or delete company records.

The 5 Operations

create

Adds a new company. Fails with a clear error if the name already exists — tells the agent to use update instead. Adds created_at timestamp. Calls save_companies() atomically.

read

Returns one company's data (by name) or all companies if company_name="all". Read-only — no file write.

update

Merges new fields into the existing company entry using .update(). Adds updated_at timestamp. Returns the full merged entry.

delete

Removes a company entry by name. Returns an error if not found. Saves atomically.

list

Returns just the list of company names and a count. Lightweight — no full data returned.

Why atomic writes matter

If the process crashed halfway through writing companies.json, you'd get a half-written, corrupt file. By writing to companies.tmp first and then rename()-ing it, the OS guarantees the swap is instant — the file is either old or new, never in between.

3
show_on_dashboard(companies_data, mode)
Tool 3 — Dashboard Generator + Launcher
@mcp.tool()

What it does: Reads the company database, generates a complete Python dashboard file, validates it, kills any old dashboard process, and starts a new one.

  1. Load all companies + logs — reads current state of both JSON files.
  2. Auto-detect mode — if more than 1 company exists, switches to "comparison" mode automatically.
  3. Call _generate_prefab_code() — builds the full Python dashboard file as a string (explained below).
  4. Validate with py_compile — writes the code to a temp file, runs Python's compile checker. Rejects invalid code before it can break the dashboard.
  5. Write generated_app.py — overwrites the file with the validated code.
  6. Kill old prefab process — reads the PID from prefab.pid and kills the old process, then runs pkill -f "prefab serve" as a cleanup.
  7. Resolve how to launch prefab — tries 3 strategies: (a) prefab in PATH, (b) prefab next to the Python executable in the venv, (c) uv tool run --from prefab-ui prefab serve.
  8. Launch new prefab process — starts prefab serve generated_app.py --port 5175 as a background subprocess, saves its PID to prefab.pid.
  9. Return success — returns URL, company count, and mode to the agent.

_generate_prefab_code() — the code generator

This private function builds the entire generated_app.py as a Python f-string template. Here's what it does before writing the template:

Base64 embedding

All company data and log data are JSON-encoded, then base64-encoded and baked into the generated file as string literals. This avoids any escaping issues with special characters in company names or descriptions.

Chart data pre-computed

Industry counts, bar chart data (company age, CAGR, share price), sparkline data, and financial data are all computed at generation time and embedded as Python repr() literals. The dashboard itself doesn't do any computation.

5 tab-builder functions

The template includes build_overview_tab(), build_comparison_tab(), build_search_tab(), build_log_tab(), and build_stats_tab() — each returns a tree of Prefab UI components.

Completeness scoring

_completeness(company) checks 5 key fields (description, summary, founded, key_people, industry) and returns a 0–100% score used for the progress bars and data quality badges.

agent.py

The AI Agent — How It Works

The agent is the orchestrator. It takes a user prompt, connects to the MCP server, and runs a loop where it alternately asks Gemini "what to do next" and executes the suggested tool calls.

The ReAct Loop

ReAct = Reasoning + Acting. Each iteration: Gemini reasons about the current state and either produces text (done) or produces function calls (keep going).

Key functions in agent.py

run_agent(prompt)

The main async function. Connects to MCP, discovers tools, builds the Gemini client, and runs the ReAct loop. Handles ConnectionRefusedError gracefully if the MCP server isn't running.

_mcp_tool_to_gemini(tool)

Converts an MCP Tool object (which has a JSON Schema) into the format Gemini expects for function declarations. Gemini only accepts a subset of JSON Schema — this function strips unsupported fields.

_clean_schema(schema)

Recursively removes JSON Schema fields that Gemini rejects (e.g. additionalProperties, $schema). Only keeps: type, properties, required, description, enum, items, anyOf.

_extract_tool_result(raw)

FastMCP can return results as a dict, a list of content items, or raw strings. This function normalises all three formats into a plain Python dict for consistent handling.

_print_tool_call / _print_tool_result

Pretty-print helpers for the terminal output. Shows each tool call with indented JSON arguments, and truncates very long results to 800 chars to keep the terminal readable.

main()

Entry point. If arguments are passed on the command line, uses them as the prompt. Otherwise shows the demo prompt and waits for user input. Calls asyncio.run(run_agent(prompt)).

Retry logic

Gemini API can return 429 RESOURCE_EXHAUSTED (rate limit) or 503 UNAVAILABLE (overloaded). The agent retries up to 3 times with increasing backoff:

for attempt in range(3):
    try:
        response = await gemini_client.aio.models.generate_content(...)
        break
    except Exception as api_err:
        if "429" in err_str or "503" in err_str:
            wait = 10 * (attempt + 1)   # 10s, 20s, 30s
            await asyncio.sleep(wait)
        else:
            raise

Two Workflows (controlled by the prompt)

Workflow A — Web Fetch

Triggered when prompt says "fetch" or doesn't specify otherwise.

  1. Call fetch_company_info for each company (real web data)
  2. Gemini enriches with financial data from its own knowledge
  3. Save with company_file_crud
  4. Call show_on_dashboard once at the end
Workflow B — LLM Knowledge Only

Triggered when prompt says "use LLM knowledge", "no fetch", or "skip fetch".

  1. Skip fetch_company_info entirely
  2. Gemini builds the full dict from training knowledge
  3. Save with company_file_crud
  4. Call show_on_dashboard once at the end

The System Prompt

The SYSTEM_PROMPT is prepended to every conversation. It tells Gemini exactly which tools are available, what each field should look like, the two workflows, and the rules (e.g. "if create fails with 'already exists', immediately retry with update"). This is what makes the agent behave consistently without needing code changes.

generated_app.py + Prefab UI

The Live Dashboard — 5 Tabs Explained

Every time show_on_dashboard is called, a fresh generated_app.py is written and the Prefab server restarts. The dashboard is a complete snapshot of the current data.

Tab 1 — Overview

One Card per company. Shows: description, summary, industry, founded year, share price, 5yr CAGR, market cap, key people, and a Progress bar for data completeness (0–100%).

The completeness badge turns green ≥80%, yellow ≥50%, red below 50%.

Tab 2 — Comparison

Three BarCharts: 5yr CAGR %, current share price, and company age (years since founding). Below that, a full comparison table with all companies side-by-side.

Requires at least 2 companies — shows a hint message if only 1 is loaded.

Tab 3 — Search & Add

An Input + Button UI for entering company names, plus a Sparkline chart of how many companies were added per day. The button is decorative — actual adding happens via the agent CLI.

Tab 4 — Agent Log

Every single operation logged by the agent, newest first. Each row shows: operation badge (ADD/FETCH/UPDATE/DEL), company name, tool name badge, date and time in UTC. No cap — all entries shown.

Tab 5 — Stats

Summary cards (total companies, avg data quality, total ops, most active company, best 5yr CAGR). A PieChart of industry distribution. Per-company quality scores with progress bars.

Why is it auto-generated code, not a fixed template?

Because the data changes on every agent run. The chart data, company lists, and log entries are all dynamic. By generating Python code with the data embedded as base64 literals, Prefab can serve the dashboard with zero network calls — everything is self-contained in one file. This also means the dashboard works offline.

End-to-End

Complete Data Flow — One Company, Start to Finish

1. User types: "Fetch info about Infosys and show the dashboard"
2. agent.py sends this + SYSTEM_PROMPT to Gemini 2.0 Flash
3. Gemini responds with a function call: fetch_company_info("Infosys")
4. agent.py sends this call to the MCP server via FastMCP Client (SSE, port 8000)
5. mcp_server.py → fetch_company_info runs: hits Wikipedia API → gets description + summary. Hits DuckDuckGo API → gets industry + key people. Runs regex for founded year. Calls append_log("fetch", "Infosys", "fetch_company_info"). Returns dict with 9 fields.
6. agent.py receives result, appends it to conversation history, sends back to Gemini
7. Gemini responds with another function call: company_file_crud(operation="create", company_name="Infosys", data={...enriched dict...})
8. mcp_server.py → company_file_crud runs: checks company doesn't already exist. Writes to companies.tmp, renames to companies.json. Calls append_log("create", "Infosys", "company_file_crud"). Returns success.
9. Gemini responds with: show_on_dashboard(mode="comparison")
10. mcp_server.py → show_on_dashboard runs: reads companies.json, reads agent_log.json, calls _generate_prefab_code(), validates with py_compile, writes generated_app.py, kills old prefab process, starts new prefab serve generated_app.py --port 5175, saves PID. Returns success + URL.
11. Gemini sees success — returns final text: "Done! Dashboard is live at http://127.0.0.1:5175"
12. agent.py detects no more function calls — prints final summary and exits.
13. Browser → http://127.0.0.1:5175 → Prefab serves the dashboard. User sees all 5 tabs with Infosys data, charts, and the log showing all 3 operations.

Why are generated_app.py and data/ gitignored?

generated_app.py

Created fresh every time show_on_dashboard is called. It embeds a snapshot of the current data as base64. Committing it would mean committing a binary blob that changes on every agent run — useless noise in git history. Anyone who clones the repo gets it regenerated on first use.

data/companies.json + agent_log.json

Runtime state — they grow and change every time the agent runs. Not source code. Each developer/user has their own company database. These files are created automatically by ensure_data_files() on first server startup.

.env

Contains your GEMINI_API_KEY. If this were committed, your API key would be public in git history forever — even if you deleted it later. Always gitignored, always.
